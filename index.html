The one fact that changes everything else

Read first

NEXT_PUBLIC_* values are baked into the Docker image at build time, not read at runtime. This is a hard Next.js constraint. Concretely: NEXT_PUBLIC_TENANT_ID, NEXT_PUBLIC_CLIENTAPP_CLIENT_ID, NEXT_PUBLIC_API_SCOPE, and NEXT_PUBLIC_CLIENT_LOOPBACK_URL all get compiled directly into the client-side JS bundle.

You cannot take the image already built for the current tenant and point it at a different tenant's App Service by changing Application Settings — the client bundle would still try to sign in against the original tenant/app registration. A new tenant needs a freshly built image, from this same source, using their own .env.production.local.

Everything else — AZURE_TENANT_ID, AZURE_CLIENT_ID, AZURE_CLIENT_SECRET, every COSMOS_*, every DB_*/AZURE_SQL_*, SQL_USE_AZURE_AD, COSMOS_USE_MANAGED_IDENTITY, REPORTS_ALLOWED_HOSTS — is read from process.env at runtime. Those genuinely can live purely as Azure App Service Application Settings, no rebuild needed.

01

Azure AD app registrations

Two registrations, in the new tenant, mirroring the split this project already went through once — get it right from day one instead of repeating the old single-registration mistake.

1a · SPA registration — public client, sign-in only, no secret

  • Redirect URI (SPA platform): the new tenant's real App Service URL once known, e.g. https://<their-app-name>.azurewebsites.net — and http://localhost:3000 if anyone will run this checkout locally against their tenant.
  • No client secret. Nothing else non-default needed.

Record: Tenant ID and Application (client) ID.

1b · API registration — confidential client, the JWT audience

  • Expose an API → set an Application ID URI (the default api://<api-client-id> is fine) → add a scope named exactly access_as_user.
  • Certificates & secrets → a client secret only if local dev needs the DefaultAzureCredential fallback path — production should use Managed Identity instead and can leave this unset.
  • Back on the SPA registration → API permissions → add this registration's access_as_user delegated permission → grant admin consent.
Scope check

App Roles are not required for this app to function — the access token's roles claim is read and displayed on /profile, but nothing currently branches on it. Skip App Roles unless the new tenant specifically asks for role display.

03

Cosmos — the web-config document

Container, once: database — any name (→ COSMOS_DATABASE_ID). Container — any name (→ COSMOS_CONTAINER).

Simplify

Partition key path: use /id. The existing production container uses a redundant same-named field as its partition key — purely a historical choice, not a code requirement. The point-read only ever needs the partition key value to equal the document's own id; /id gets the same behavior with one less field to maintain.

Document, once — id must match COSMOS_DOCUMENT_ID (or literally sidebar-config if that's left unset):

cosmos · sidebar document
// id must equal COSMOS_DOCUMENT_ID (or "sidebar-config" if unset)
{
  "id": "sidebar-config",
  "variables": [],
  "menu": [
    {
      "title": "Main",
      "path": "",
      "items": [
        { "path": "", "title": "Home", "icon": { "src": "Home" } },
        { "path": "profile", "title": "Profile", "icon": { "src": "User" } }
      ]
    }
    // one entry per report — this project's own local dev seed data has a
    // large real-shaped example. Built for a local dev emulator, though —
    // don't reuse its values for a real tenant.
  ]
}

Full shape reference: types/sidebar.d.ts, types/tables.d.ts.

04

Cosmos — the alias-config document

This is the piece flagged as unfamiliar territory in the team-chat note — worth reading slowly.

Not configurable

The document's id must be exactly alias_config — a literal string in the alias resolver's Cosmos query, not COSMOS_DOCUMENT_ID (that setting only controls the sidebar document's id). It lives in the same database/container as Phase 03. Its array field must also be named exactly alias_config.

cosmos · alias document
// id is always this literal string, never env-configurable
{
  "id": "alias_config",
  "alias_config": [
    {
      // SQL-backed alias
      "id": "orders-alias",
      "sqUrl": "your-sql-server.database.windows.net",
      "sqDatabase": "OrdersDB",
      "sqUser": "acfreport_reader",
      "sqPassword": "<the login's password>"
      // omit sqUser + sqPassword TOGETHER to use Managed Identity instead
      // "sqPort": 1433   — optional, only for non-standard ports
    },
    {
      // Cosmos-backed alias
      "id": "cosmos-default",
      "databaseId": "ExampleDB"
      // omit endpoint/key to reuse this app's own Cosmos account
    }
  ]
}

A report's report.alias field is just an id lookup into this array. More real-shaped examples: scripts/dev/seed-data/alias_config.json (again — built for the local emulator, not for reuse verbatim).

05

SQL Server access

Worth being deliberate here, not just "make it connect" — see the security note at the end.

Network

If it's Azure SQL, the firewall needs a rule letting the App Service reach it — either "Allow Azure services and resources to access this server" (broad, simplest for a pilot) or the App Service's specific outbound IPs (tighter, more setup).

Choose an auth model per alias

SQL login — simpler, recommended for a pilot:

sql · on the target server, then database
CREATE LOGIN acfreport_reader WITH PASSWORD = '<strong password>';
-- then, inside the target database:
CREATE USER acfreport_reader FOR LOGIN acfreport_reader;

That login/password is exactly what goes into the alias's sqUser/ sqPassword fields (Phase 04).

Managed Identity — more setup, no password to manage. Requires the SQL Server to have an Azure AD admin configured first:

sql · inside the target database
CREATE USER [<app-service-name>] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [<app-service-name>];

Omit both sqUser and sqPassword on that alias to select this path. Only set SQL_USE_AZURE_AD=true if every alias should go this way — it's an all-or-nothing switch that overrides aliases which do have their own SQL login set.

Permission needed: SELECT, nothing more

Confirmed directly in the report-fetching source: every SQL report type executes its configured query as a read-only subquery — there is no write path anywhere in the code. Grant db_datareader on the target database (simplest), or narrower per-table GRANT SELECT if scoping to exactly what the pilot's reports touch.

Security note

A report's SQL query is author-typed in the sidebar config, not client input — but the columns available for searching/filtering/sorting on top of it come from the database's own metadata for that exact query, which only ever exposes columns the query itself selects. Whatever tables/views the report authors write into their queries are what the SQL login's grant needs to cover, and only those — don't grant broader db_datareader-on-everything than the pilot's actual reports need, especially on a server you don't yet have a feel for.

General principle-of-least-privilege practice, not specific to this app: grant a reporting login only what it needs to serve the reports actually configured, and revisit that grant whenever a new report is added — rather than issuing broad access up front on a server you don't yet have a full picture of.

06

Build and deploy the image

Do not reuse the image already built for the current tenant — see the opening note. Rebuild from this same source, using the new tenant's own .env.production.local (Phase 01 + 02's values):

shell
./scripts/docker-build.sh .env.production.local <new-tenant-image-tag>

Recommend the new tenant have their own Azure Container Registry — cleaner separation for a genuinely different client engagement, even if reusing the existing one is technically reachable given the right permissions.

The full release script bundles build + push + rollout together, but it's written specifically against the current tenant's own ACR/App Service/resource-group names. For a different tenant, either edit a copy of it with their values, or do the three steps by hand:

shell
docker tag <new-tenant-image-tag> <their-acr-name>.azurecr.io/<image-name>:<tag>
az acr login --name <their-acr-name>
docker push <their-acr-name>.azurecr.io/<image-name>:<tag>
az webapp sitecontainers update --name <their-app-service-name> \
  --resource-group <their-resource-group> --container-name main \
  --image <their-acr-name>.azurecr.io/<image-name>:<tag>

Open questions before calling this final

  • Whether the pilot wants Managed Identity for Cosmos/SQL from day one, or plain key/password auth for simplicity now with a migration later.
  • Whether any report needs App Roles or role-gated visibility — nothing in the app currently branches on the roles claim, so this only matters if specifically requested.
  • Confirm with whoever owns the new tenant's SQL Server what else already lives on it before granting db_datareader broadly.
